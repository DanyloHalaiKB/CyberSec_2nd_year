## Крок 1–2. GitHub

1. Створити акаунт на [github.com](https://github.com) (якщо ще немає).
2. Створити **порожній публічний** репозиторій, наприклад `cv-web-lab`.
   Не додавати README, .gitignore чи ліцензію — інакше історії розійдуться.
3. У терміналі VS Code, перебуваючи в цій теці:

```bash
git remote add origin https://github.com/<ваш-нік>/cv-web-lab.git
git branch -M main
git push -u origin main
```

Якщо Git попросить логін — замість пароля вводиться **Personal Access Token**
(GitHub → Settings → Developer settings → Personal access tokens), бо автентифікацію
паролем GitHub вимкнув.

4. Зробити скріншот сторінки репозиторію (має бути видно `index.html` у корені) →
   покласти у `screens/`, посилання на репозиторій додати у звіт.

## Крок 3. Vercel — Частина 1 (статичний сайт)

1. Зареєструватись на [vercel.com](https://vercel.com), під час реєстрації одразу
   підключити акаунт GitHub (**Continue with GitHub**).
2. **Add New → Project** → знайти свій репозиторій → **Import**.
3. Налаштування:

| Поле | Значення | Чому |
|---|---|---|
| Project Name | `cv-static` | довільна назва |
| Framework Preset | **Other** | фреймворків немає, це чистий HTML/CSS/JS |
| Root Directory | `./` | `index.html` лежить у корені репозиторію |
| Build Command | *(порожньо)* | статичний сайт не потребує збірки |
| Output Directory | *(порожньо)* | віддаються файли «як є» |

4. **Deploy** → дочекатись «Congratulations!» → **Continue to Dashboard** →
   скопіювати домен виду `cv-static-xxxx.vercel.app`.
5. Скріншот розгорнутого сайту → `screens/`.

## Крок 3 (b). Vercel — Частина 2 (React-застосунок)

React-проєкт лежить **у підтеці**, тому для нього створюється **окремий проєкт Vercel**
із того самого репозиторію:

1. **Add New → Project** → той самий репозиторій → **Import**.
2. Налаштування:

| Поле | Значення |
|---|---|
| Project Name | `cv-react` |
| Root Directory | **`lab_2_react`** ← натиснути **Edit** і вибрати підтеку |
| Framework Preset | **Vite** (Vercel визначить автоматично) |
| Build Command | `npm run build` |
| Output Directory | `dist` |
| Install Command | `npm install` |

3. **Deploy** → скопіювати домен, зробити скріншот.

## Крок 4. Перевірка автоматичного оновлення

Другий коміт уже підготовлений локально. Після першого пушу достатньо:

```bash
git log --oneline          # переконатись, що обидва коміти на місці
git push                   # якщо другий коміт ще не запушений
```

Vercel через вебхук GitHub отримає подію `push`, запустить нову збірку й підмінить
продакшн-деплой. На сайті акцентний колір зміниться з фіолетового на зелений.

Посилання на коміт для звіту має вигляд:
`https://github.com/<ваш-нік>/cv-web-lab/commit/0085583`

`CNAME` на `cname.vercel-dns.com` (для `www`). HTTPS-сертифікат Vercel випустить сам.

## Питання для самоконтролю

**1. Що саме завантажує браузер, коли відкриває розгорнутий статичний сайт?**
Спершу `index.html`, потім — за посиланнями в розмітці — `styles.css`, `script.js`,
шрифти й зображення. Усе це статичні файли, роздані CDN-серверами Vercel; жоден код
на сервері при цьому не виконується.

**2. Що дає підключення Git-репозиторію до хостингу порівняно з ручним завантаженням?**
Автоматичне розгортання на кожен push, відтворювані збірки (платформа сама ставить
залежності), історія деплоїв із миттєвим відкотом (Instant Rollback), preview-деплої
для кожної гілки й pull request, відсутність людських помилок на кшталт «забув
завантажити один файл».

**3. Що відбувається між `git push` і появою оновленої сторінки?**
(1) GitHub відправляє вебхук на Vercel; (2) Vercel клонує потрібний коміт;
(3) виконує Install Command (`npm install`); (4) виконує Build Command (`npm run build`);
(5) бере вміст Output Directory (`dist`) і розкладає його по CDN; (6) переводить
продакшн-домен на новий деплой. Для статичного сайту кроки 3–4 пропускаються.

**4. Для чого налаштування Root Directory і коли його змінюють?**
Воно вказує, яку підтеку репозиторію вважати коренем проєкту. Типове значення `./`
змінюють, коли в одному репозиторії кілька застосунків (монорепо) — як у цій роботі:
для React-проєкту вказано `lab_2_react`, і саме там Vercel шукає `package.json`.

**5. Чому звичайний HTML-сайт не потребує збірки, а Vite-проєкт потребує? Що створює `npm run build`?**
Браузер розуміє HTML, CSS і JS напряму. Він **не** розуміє JSX, ESM-імпорти з
`node_modules` за назвою пакета й директиви Tailwind. `npm run build` компілює JSX у
звичайний JS, збирає всі модулі в кілька бандлів, генерує CSS із використаних утиліт,
мініфікує код і додає хеші до імен файлів (для інвалідації кешу). Результат — тека
`dist/` зі звичайними статичними файлами.

**6. Що таке Output Directory і чому для Vite це `dist`?**
Тека, вміст якої платформа роздає як готовий сайт. Vite за замовчуванням кладе
результат збірки в `dist/` (у Next.js це `.next`, у Create React App — `build`).

**7. Чим відрізняється production-деплой від preview?**
Production обслуговує основний домен і створюється з головної гілки (`main`).
Preview створюється для будь-якої іншої гілки або pull request, отримує власну
тимчасову URL-адресу й дозволяє перевірити зміни, не чіпаючи робочий сайт. Тобто
push у гілку, відмінну від головної, створює **preview**.

**8. Чому `node_modules/` не тримають у репозиторії?**
Сотні мегабайтів і десятки тисяч файлів, які до того ж залежать від ОС і версії Node
(скомпільовані бінарники). Замість них комітять `package.json` і `package-lock.json` —
цього достатньо, щоб `npm ci` відтворив **точно ті самі** версії залежностей на будь-якій
машині.

**9. Хто видає HTTPS-сертифікат, якщо ми нічого не налаштовували?**
Платформа автоматично отримує безкоштовний сертифікат від центру сертифікації
Let's Encrypt, підтверджує володіння доменом через ACME-протокол, встановлює сертифікат
на свої edge-сервери й далі сама його продовжує кожні ~90 днів.

**10. Розгортання завершилось помилкою — де шукати причину?**
У **Build Logs** деплою. Там видно те, чого не видно в репозиторії: реальні версії Node
і npm на збирачі, помилки встановлення залежностей, повний вивід компілятора, помилки
типізації чи лінтера, відсутні змінні середовища. Найчастіші причини: не заданий Root
Directory, інша версія Node, ніж локально, пакет був лише в локальному `node_modules`
і не потрапив у `package.json`, а також чутливість Linux до регістру в іменах файлів
(`./Components/Header` проти `./components/Header` — на Windows працює, на збирачі ні).
